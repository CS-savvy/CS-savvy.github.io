## Optimization Approach

### 1. Model Conversion to TensorRT

TensorRT is NVIDIA's inference optimizer and runtime, built to squeeze low latency and high throughput out of trained models by restructuring and recompiling them for a specific GPU target. The general pipeline is: export the trained model to ONNX, then build a TensorRT engine from that ONNX graph, optionally applying precision calibration along the way.

Under the hood, the builder applies a few standard techniques worth naming in a technical writeup:
- **Layer fusion** — collapsing chains like Conv → BatchNorm → ReLU into a single CUDA kernel, cutting kernel-launch overhead.
- **Kernel auto-tuning** — picking the fastest available kernel implementation for the target GPU (A100, RTX, Jetson, etc.) rather than a generic one.
- **Precision calibration** — converting FP32 weights down to FP16 or INT8 where accuracy allows.
- **Dynamic tensor memory** — pooled memory allocation to cut per-inference overhead.

### 2. Batching Strategy

For receipt-layout documents with variable sizes, dynamic batching is generally the right call over static batching. As a rule of thumb from NVIDIA's own optimization guidance, when a network includes matrix-multiply layers, batch sizes in multiples of 32 tend to perform best for FP16/INT8 inference, since that's what lets Tensor Cores be fully utilized on supported hardware.

### 3. Precision Tuning

TensorRT supports running individual layers in FP32, FP16, BF16, FP8, or INT8, and by default picks whichever precision gives the best performance for that layer. The general trade-off:

- **FP16** is usually the best starting point for the accuracy/performance balance — commonly cited as roughly half the memory footprint and meaningfully faster inference versus FP32, with public benchmarks showing accuracy drops in the low single digits depending on the model and dataset.
- **INT8** pushes further — public examples report model size reductions of around 70% versus FP32 with in some cases negligible additional accuracy loss over FP16 — but it typically requires a calibration dataset that's representative of your real traffic (in your case, receipt layouts across the languages/currencies/merchants you support).
